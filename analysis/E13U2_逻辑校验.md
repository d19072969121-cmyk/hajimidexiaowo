## 1. 错题本族判据 —— 通过

`src/features/chat/plugins/modes/modeFamily.ts` 是**单一真相源**：

```ts
export const ANALYSIS_FAMILY_MODES: readonly string[] = ['analysis', 'solver'];
export function isAnalysisFamilyMode(mode: unknown): boolean {
  return typeof mode === 'string' && ANALYSIS_FAMILY_MODES.includes(mode);
}
```

该文件头注释明确列出了「写死 `mode === 'analysis'` 会静默失效」的四类症状，其中第三条正是：

> - `useMistakeBook` 漏掉 solver → **新拍的题不进错题本**

即：**API 层面 `isAnalysisFamilyMode('solver') === true`，错题本收录 solver 有保障。** ✅

## 2. `useMotionPresence` 状态机 —— 通过

修复后（本轮我提交）：

```ts
if (open) {
  setMounted(true);
  setExiting(false);
  if (reduced || enter === 'animation') {
    setShown(true);
  } else {
    setShown(false);
    frame = requestAnimationFrame(reveal);
    enterTimer = setTimeout(reveal, ENTER_FRAME_FALLBACK_MS);  // 48ms
  }
}
```

**收敛性论证（双路径）：**

1. `open` 保持 true 且 effect 未重跑 → `setTimeout(reveal, 48)` 必然在 ≤48ms 内触发 → `shown = true`
2. `open` 保持 true 但 effect 重跑（依赖变化）→ cleanup 清掉旧 `enterTimer`，**新 effect 重新挂一个** →
   同样必然触发

**关键点：`reveal` 是无条件 `setShown(true)`，不依赖任何可能失效的中间状态。**
被 cancel 的只是"旧定时器/旧帧"，新 effect 总会补上新的。这正是旧实现（`frame2` 被 cancel 后**再没有任何补偿路径**）与修复版的本质差别。

**「乱序覆盖」风险评估**：`reveal` 归 cleanup 所有，被 cleanup 清除的 timer 不会触发；
仍存活的 timer 只可能属于**当前** effect 实例。因此不存在"旧 reveal 把新 `setShown(false)` 覆盖掉"的窗口。✅

配套测试：`src/hooks/__tests__/useMotionPresence.race.test.tsx`（8 例），
覆盖「帧被取消」「依赖变化打断」「重渲染风暴」「关闭语义不变」「重开清理关闭计时器」。

## 4. 🔴 发现缺陷：`useSessionLifecycle.ts:80` 仍写死 `['analysis']`

### 4.1 事实

| 位置 | 写法 | 状态 |
|---|---|---|
| `src/features/chat/hooks/useSessionManagement.ts:95` | `const SIDEBAR_EXCLUDE_MODES = [...ANALYSIS_FAMILY_MODES];` | ✅ 已修 |
| `src/features/chat/pages/ChatV2Page.tsx:582` | `isAnalysisFamilyMode(store.getState().mode) ? 'analysis' : 'other'` | ✅ 已修 |
| **`src/features/chat/pages/useSessionLifecycle.ts:80`** | **`const SIDEBAR_EXCLUDE_MODES = ['analysis'];`** | 🔴 **未修** |

`useSessionLifecycle.ts` 内共 **7 处**消费该常量（:87, 319, 327, 332, 335, 386），
全部继承了写死值，`solver` 一律漏排除：
· :87 `chat_v2_count_sessions` —— 未分组计数
· :319/:327/:332/:335/:386 —— 会话列表/分页/active 过滤

### 4.2 该处源码注释与实现自相矛盾

```ts
// 与 useSessionManagement 的列表口径保持一致：拍题（analysis）会话不进首页计数，
// 否则「列表已排除、计数没排除」会让总数偏大、hasMore 判断错误（翻到空页）。
const SIDEBAR_EXCLUDE_MODES = ['analysis'];
```

注释**明确声称**要与 `useSessionManagement` 口径一致，但 `useSessionManagement` 早已改为族判据。
**注释描述的意图是对的，实现没跟上** —— 这正是这个 bug 的典型形态。

### 4.3 为什么现有测试没抓住

`src/features/chat/hooks/__tests__/sidebarExcludeModes.solver.test.ts` **只覆盖了一个文件**：

```ts
const HOOK_PATH = resolve(process.cwd(),
  'src/features/chat/hooks/useSessionManagement.ts');   // ← 只读这一个
...
expect(src).not.toMatch(/const SIDEBAR_EXCLUDE_MODES = \['analysis'\]/);  // ← 只对这个文件断言
```

而且它是**路径硬编码**的 source 测试 —— `useSessionLifecycle.ts` 不在 `HOOK_PATH`，
即使里面写着完全相同的违规字符串，正则也扫不到。

**这是"修了一处、漏了另一处"的漏网，测试的写法（单文件硬编码）决定了它抓不到同类问题。**

### 4.4 影响

`solver`（拍题解题 agent）会话：
- 错题本：**进**（`useMistakeBook` 走 `isAnalysisFamilyMode`）
- 首页会话列表：**不进**（`useSessionManagement` 已用族判据）
- **首页未分组计数 / hasMore 判断：进**（`useSessionLifecycle` 写死，漏排除 solver）
- ChatV2Page 三态守卫：**不进**（:582 已用族判据）

→ 同一会话在**计数口径**与**列表口径**上归属不一致，
即注释里亲口警告的「列表已排除、计数没排除 → 总数偏大、hasMore 判断错误（翻到空页）」，
对 `solver` 会话**依然成立**。

### 4.5 建议（未擅自改，等你定）

1. **改法**（一行，与 `useSessionManagement` 对齐）：

   import { ANALYSIS_FAMILY_MODES } from '../plugins/modes/modeFamily';
   const SIDEBAR_EXCLUDE_MODES = [...ANALYSIS_FAMILY_MODES];

   对**每一处**断言必须由 `ANALYSIS_FAMILY_MODES` 派生。
   这样将来第五个消费点出现时也会被自动捕获。
