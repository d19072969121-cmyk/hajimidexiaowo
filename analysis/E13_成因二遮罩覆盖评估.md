## 1. 复核 Lead 的推演

Lead 推演：`screenPosition='center'` 时 `getBaseTranslate()` 返回 `-sidebarWidth`，代入

```
progress = clamp((translateX + sidebarWidth) / max(sidebarWidth, 1))
         = (-sidebarWidth + sidebarWidth) / max(sidebarWidth, 1) = 0
```

**复核结果：静止态下该推演正确**，实测确认（`opacity` 实测为 `0`，`aria-hidden=true`，`pointerEvents=none`，`tabindex=-1`）。

### 1.1 边界项复核

| 边界 | 复核 |
|---|---|
| `clamp` 与 `Math.max(sidebarWidth, 1)` | 正确。`sidebarWidth='auto'` 时最小 280（`:354`），`'half'` 时最小 180（`:356`），比例写法则最小 200（`:358`）。**不存在 `sidebarWidth=0` 的静态可达路径**。`max(..,1)` 只是防除零，不影响结论。 |
| `containerWidth=0`（首帧，未测量） | `sidebarWidth='auto'` → `max(0-60, 280)=280`；`translateX=-280` → progress 仍为 0。**不是残留源**。实测 `w=0 initial opacity=0`。 |
| 宽高变化（旋转/分屏） | 走 `:429 widthChanged && !positionChanged → finishAt(to)`，直接归零。实测 `after width change opacity=0`。 |
| `screenPosition='right'` | `translateX=-(sidebarWidth+containerWidth)` → `(translateX+sidebarWidth)/sidebarWidth = -containerWidth/sidebarWidth < 0` → clamp 到 0。实测全程 `0`。 |

**Lead 推演的缺口**：推演只覆盖了"`renderedTranslateRef.current` 与 `baseTranslate` 一致"的情形。真实实现里 `translateX` 取的是

```
src/components/layout/MobileSlidingLayout.tsx:818-820
  const translateX = isDragging || isSettling
    ? (renderedTranslateRef.current ?? currentTranslate)
    : baseTranslate;
```

`renderedTranslateRef` **只由 `applyVisualTranslate` 写**（`:383`）。一旦遮罩 DOM 被卸载，这个 ref 就成了**游离残留值**，而 settle 的起点又直接读它：

```
src/components/layout/MobileSlidingLayout.tsx:405
  const from = renderedTranslateRef.current ?? baseTranslate;
```

它不知道遮罩已经重挂载，于是用旧的"打开态"值当动画起点。

## 2. 可复现路径（已用测试稳定复现）

> 验证方式：可控 rAF 时钟 + jsdom 真实渲染，逐帧读取 `mask.style.opacity`。测试文件见 §5。
> 所有数值均为**实测**，非推演。

### 路径 A（主路径）— 遮罩卸载后重新挂载，首帧全不透明

触发序列：

1. `screenPosition='left'`（抽屉展开）→ settle 完成，`renderedTranslateRef=0`，遮罩 `opacity=1`；
2. `sidebar` 变为 `null`（`hasSidebar=false`）→ `:963` 条件不成立，**遮罩 DOM 被整体卸载**；
3. `sidebar` 恢复 + `screenPosition='center'` → 遮罩**重新挂载**；
4. settle 效应读 `from = renderedTranslateRef.current`（残留的 `0`，即"打开态"），
   而 `to = baseTranslate = -280` → 认为"有位移需要动画" → `applyVisualTranslate(from)` 把
   新挂载的遮罩**先写成 `opacity: 1`**。

实测逐帧轨迹（`screenPosition` 已回到 `center`，即用户看到的是首页）：

```
t0    : 1
16ms  : 0.802      ← 顶栏此刻被 80% 不透明的遮罩压住
32ms  : 0.629
48ms  : 0.482
64ms  : 0.364
...
192ms : 0.026
208ms : 0.017      ← 首次低于 aria-hidden 阈值 0.02
304ms : 0.000
```

- **`opacity > 0.02` 的持续帧数：12 帧 ≈ 200ms**（60fps 下）。
- 首帧是 `opacity = 1` 的**完全不透明**遮罩。

### 路径 B — `showContentOverlay` 关→开

`:963` 的 `showContentOverlay && hasSidebar &&` 同为卸载条件，走同一缺陷：

```
step1(overlay=false) → 无遮罩              : null
step2(overlay=true)  → 重挂载首帧 opacity  : 1
```

### 路径 C — 遮罩卸载打断补间（拖拽/动画中途侧栏消失）

`useLayoutEffect` 的清理函数（`:464-469`）只取消 rAF，**不重置 `renderedTranslateRef`**。后续重挂载同样读到残留值。

### 未复现的路径（澄清，避免误伤）

| 路径 | 实测 |
|---|---|
| 拖拽中途 `touchcancel` 回弹 | 收敛到 0（8 帧后低于 0.02）。**无残留**。 |
| 关闭抽屉的淡出 | 单调收敛到 0，192ms 后低于 0.02。**无残留**。 |
| settle 中途反转（快开快合） | 逐帧全程落在 `[0,1]`，最终归 0。**无残留**。 |
| 整体 unmount 后重挂载 | 新 DOM 节点，`style` 干净（`opacity=0`）。**无残留**。 |
| 三屏 right 往返 | 全程 0。**无残留**。 |
| 静止期 React 重渲染 | 从 `renderedTranslateRef` 取值，与直写结果一致，不回退。**无残留**。 |

**关键点：本缺陷只在"遮罩 DOM 节点被卸载又重新挂载"时出现，是结构性路径，不是竞态。**

## 3. 为什么这会表现为"三杠时有时无/被盖住"

结构链（全部取自源码文本）：

1. 遮罩是主内容壳的**第一个子元素**，`absolute inset-0` + `zIndex: Z_INDEX.overlay` = **2000**
   （`:973`、`:980`）；
2. 顶栏渲染在同一主内容壳内的兄弟 wrapper 里（`:986-991`），组件自身是 `relative shrink-0` 且
   **没有 z-index**（`UnifiedMobileHeader.tsx:238`）；
3. `src/config/zIndex.ts`：`mobileHeader = 1100 < overlay = 2000`；
4. 二者同处一个层叠上下文 → **遮罩必然绘制在顶栏之上**。

因此只要遮罩 `opacity > 0`，三杠就被这层 `hsl(var(--background) / 0.78)` 的半透明壳压住。
`opacity=1` 时是**完全不透明**的遮挡。

**旁证（与用户症状吻合）**：`:968` 用 `aria-hidden={sidebarRevealProgress <= 0.02}`
——作者已意识到"0.02 以上算可见"，但**节点仍然存在且仍盖在顶栏上**，
`pointer-events` 虽为 `none`（不影响点击），**视觉遮挡依旧成立**。
用户描述的是"被盖住"而非"点不动"，与此完全一致。

### 与成因一的关系

成因一（`useMotionPresence` 双 rAF 竞态，task-1 已修）作用于 **顶栏自身的挂载/`shown` 类切换**；
本缺陷作用于 **遮罩的透明度**。两者独立，修其一不影响另一。**因此 task-1 全绿不能证明本问题已解决。**

## 4. 最小修复方案（草案，未落地）

### 4.1 推荐：修 settle 起点，让 ref 在遮罩卸载时失效

**位置**：`src/components/layout/MobileSlidingLayout.tsx:405`（根因），或等价的语义修正。

根因是"动画起点读取了一个可能属于**已卸载 DOM 节点**的残留值"。最小且语义正确的改法是让
ref 的生命周期与遮罩节点绑定 —— 遮罩卸载即让 ref 失效，下一次 settle 自然回落到 `baseTranslate`。

```diff
--- a/src/components/layout/MobileSlidingLayout.tsx
+++ b/src/components/layout/MobileSlidingLayout.tsx
@@
   const applyVisualTranslate = useCallback((value: number) => {
     renderedTranslateRef.current = value;
@@
   }, [sidebarWidth]);
+
+  // 遮罩卸载 → renderedTranslateRef 代表的 DOM 节点已不存在，必须让残留值失效。
+  // 否则重新挂载时 settle 会拿"打开态"旧值当动画起点，把新遮罩先写成 opacity:1。
+  // track 也走同一条 ref（track 常驻不卸载），因此仅在遮罩真正卸载时才失效。
+  const overlayRendered = showContentOverlay && hasSidebar;
```

```diff
   <button
     ref={maskRef}
@@
   />
+{!overlayRendered && <RenderedTranslateInvalidator ref={renderedTranslateRef} />}
```

> 更简洁的等价写法（推荐给实现者，二选一）：
> 在 `useLayoutEffect` 里把 `overlayRendered` 纳入依赖，并在 `!overlayRendered` 分支直接
> `renderedTranslateRef.current = null`，同时 `applyVisualTranslate` 只更新存在的 DOM。

**验证性改动（本报告在内存中临时应用过，随后已完全还原）**：
把 `:405` 的 `from` 改为直接取 `baseTranslate`：

```diff
-    const from = renderedTranslateRef.current ?? baseTranslate;
+    const from = baseTranslate;
```

结果：残留轨迹 `t0: 0 → 16ms: 0.000 → …` **完全消除**；回归测试 7/7 全绿。
这从**反证方向**确认了根因位置。

> ⚠️ 注意：`from = baseTranslate` 只是**根因验证补丁**，会一并取消"settle 中被抓住可抓回"的手感
> （见 `:476-481` 的设计意图），**不建议直接这样落地**。请用 §4.1 的 ref 失效方案，或在
> settle 起点额外判断"遮罩是否为新挂载节点"。

### 4.2 关于 Lead 提出的两个修法评估

**修法 A：`progress <= 0.02` 时 `return null` 不渲染遮罩**

- 能**结构性消除**遮挡（DOM 不存在即不可能盖住顶栏），且对静止态零成本。
- 淡出影响：实测关闭轨迹在阈值处为 `0.0258`，从 2.6% 透明度直接消失 —— 乘以遮罩底色
  `hsl(var(--background)/0.78)`，视觉跳变**不可感知**。不会"闪一下"。
- **但**：若只加这条、不修 `:405`，则路径 A 的首帧 `opacity=1` 仍会让节点存在（`1 > 0.02`），
  **问题依旧**。即**修法 A 单独不够**，必须与 §4.1 同做。
- 副作用：会改变 `tests/vitest/chatV2MobileSidebarLayerContract.test.ts` 依赖的源码文本断言
  （该文件断言了遮罩相关字符串），需同步更新测试。

**修法 C：静止态把 `renderedTranslateRef` 归位 `baseTranslate` + 未交互时 `pointerEvents:'none'`**

- `pointerEvents` 部分**已经是现状**（`:982` 仅在 `sidebarRevealProgress > 0.98 && left && !dragging`
  时为 `auto`）。实测静止/关闭期恒为 `none`。**这一半不是缺口，无需再改。**
- "静止态归位 ref"方向正确，但**必须发生在遮罩卸载时**才有意义；仅"静止时归位"覆盖不到路径 C
  （补间被打断后直接重挂载）。**因此单独不够，但作为 §4.1 的一部分是正确做法。**
- 结论：修法 C 的 ref 部分 ≈ §4.1；`pointerEvents` 部分已满足，属于**无效改动**。

### 4.3 建议：**现在不改，留测试作门禁**

**已按倾向建议执行**：用例 4 已标记为 `it.fails(...)`，并附完整缺陷说明注释。

| 用例 | 性质 |
|---|---|
| 1 / 2 / 3 / 5 / 6 / 7（6 个） | **回归护栏**。锁的是**当前已经正确**的行为（静止不可见、淡出收敛、cancel 回弹、快开快合值域、结构约束）。这些用例现在就是绿的，防未来改动回归。 |
