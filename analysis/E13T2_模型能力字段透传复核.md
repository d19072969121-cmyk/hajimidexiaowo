### 1.3 序列化对齐（Lead 问的 Q5）

`ModelProfile` 定义在 `llm_manager/mod.rs:3154-3156`：

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]        // ← 关键
pub struct ModelProfile { ... }
```

字段 `is_embedding` `is_reranker` `is_image_generation`（`mod.rs:3172/3174/3176`）经 camelCase 序列化为
**`isEmbedding` / `isReranker` / `isImageGeneration`** —— 与前端 TS 类型**一致**。✅

**但前端存在「双写防御」**，本身是味道：

```ts
// useAvailableModels.ts:98-101
const isEmbedding = c.isEmbedding === true || (c as any).is_embedding === true;
const isReranker  = c.isReranker  === true || (c as any).is_reranker  === true;
```

同款出现在 `ModelPicker.tsx:162-165`、`RuntimeModelMenu.tsx:91-94`、`ExamSheetUploader.tsx:350-353`、
`NoTagTreeShadPanel.tsx:97-100` 共 5 处。

**评估**：后端只发 camelCase（`#[serde(rename_all="camelCase")]` 是单向重命名，不会同时发 snake_case），故 `|| is_embedding` 分支**永不命中**，属无害冗余。**但它说明历史上曾对字段名没把握** —— 新增字段时若有人按「前端读 snake_case」的直觉去写，会踩空。**建议保持 camelCase 单一口径**，不要新增 snake_case 兜底。

## 3. 【发现的缺口】两处合并逻辑漏 `is_image_generation`

这是本次复核的**实质产出**。`is_embedding`/`is_reranker` 到处都在，`is_image_generation` 在**同步类逻辑**里缺席。

### 3.1 缺口 A：`merge_builtin_profile_user_aware`（两条分支都漏）

`llm_manager/mod.rs:4094`，**调用点 `:5755`（`get_model_profiles` 内，每次读取都跑）**。

**分支一 —— 无快照基线（`:4105-4112`）**：

```rust
let Some(previous_builtin) = previous_builtin_profile else {
    existing.is_multimodal = builtin_profile.is_multimodal;
    existing.is_reasoning = builtin_profile.is_reasoning;
    existing.is_embedding = builtin_profile.is_embedding;      // :4108
    existing.is_reranker = builtin_profile.is_reranker;        // :4109
    existing.supports_tools = builtin_profile.supports_tools;
    existing.supports_reasoning = builtin_profile.supports_reasoning;
    return;   // ❌ 没有 existing.is_image_generation = builtin_profile.is_image_generation;
};
```

**分支二 —— 有快照（`:4114-4131+`）**：

```rust
update_if_untouched!(is_multimodal);
update_if_untouched!(is_reasoning);
update_if_untouched!(is_embedding);      // :4129
update_if_untouched!(is_reranker);       // :4130
// ❌ 没有 update_if_untouched!(is_image_generation);
```

**对比证据**：同一函数的两个分支里，`is_embedding`/`is_reranker` 都成对出现（`:4108-4109`、`:4129-4130`），唯独 `is_image_generation` **两处都不在**。`grep is_image_generation mod.rs` 的全部命中（`:2775/2942/3045/3176/3251/5961/6081/6180/6245/6347`）**没有任何一处落在 4094 函数体内**。

**后果**：内置注册表把某模型的 `is_image_generation` 设为 `true`（例如新补录 `cogview-4`）后，
用户已有配置里该模型会**永远保持 `false`**（分支一根本不赋值；分支二没有 `update_if_untouched` 项）。
→ 该模型**仍被视为普通对话模型**，出现在模型选择器、被 OCR/上下文压缩当候选。

### 3.2 缺口 B：`get_model_profiles` 内的迁移补丁（`:5695-5708`）

`:5701-5705` 的触发条件只检查 4 个字段：

```rust
if profile.supports_tools != builtin.supports_tools
    || profile.is_multimodal != builtin.is_multimodal
    || profile.is_reasoning != builtin.is_reasoning
    || profile.supports_reasoning != builtin.supports_reasoning
{
    ...
    profile.is_embedding = builtin.is_embedding;   // :5707
    profile.is_reranker = builtin.is_reranker;     // :5708
    // ❌ 没有 profile.is_image_generation = builtin.is_image_generation;
    patched = true;
}
```

**双重缺陷**：
1. 赋值体缺 `is_image_generation`（与 `is_embedding`/`is_reranker` 成对出现的模式不一致）；
2. **触发条件**本身也不含 `is_image_generation` —— 即使补上赋值，若其余 4 字段恰好都一致、只有 `is_image_generation` 不同，**这段补丁根本不会进入**，标记照样丢失。

### 3.3 缺口是否被启发式掩盖？

部分掩盖，但有明确漏网。`looks_like_image_generation_model_id`（`:3312-3317`）：

```rust
["gpt-image", "dall-e", "imagen", "flux"].iter().any(|n| model.contains(n))
```

该兜底只在**转换点**生效（`:5961`、`:6347` 两处 `|| looks_like_...`）。

→ **漏网模型**：注册表已声明但**名字不含**上述四词者，如 `cogview-4`、`kolors`、`wanx`、`seedream`、`hunyuan-image` 等。
这些模型的 `is_image_generation` 一旦在 §3.1/§3.2 被丢弃，**没有任何兜底能救回**。

## 4. 【发现的缺口】`CapabilityOverrides` 不含三个能力字段

`llm_manager/mod.rs:164-169`：

```rust
struct CapabilityOverrides {
    is_multimodal: bool,
    supports_tools: bool,
    supports_reasoning: bool,
    context_window: Option<u32>,
}
```

`infer_capability_overrides_from_builtin_catalog`（`:3919`，遍历 `BUILTIN_MODELS`）在 `:3947-3952` 只填这 4 个字段，
`resolve_capability_overrides`（`:4076-4090`）也只合并这 4 个。

**评估**：这是一条**独立的能力推导旁路**，用于「用户只填了 model id 时反推能力」。它**不参与** `is_embedding`/`is_reranker`/`is_image_generation` 的主透传（那三个走 `merge_builtin_profile_user_aware` 与直接赋值）。

→ **不是当前 bug 的成因**，但**是同类隐患**：将来若有人想「凭 model id 自动识别这是 embedding 模型」，会发现这条旁路**结构上装不下**这三个字段，需要先扩结构体。
**本次不做修改建议，仅记录**（改动面大，且非 task-14 目标）。

## 5. 「漏透传」的静默失败形态（Lead 问的 Q3）

| 漏传位置 | 静默失败成什么 | 用户可见症状 |
|---|---|---|
| §3.1 分支一（无快照） | 已有配置的 `is_image_generation` 恒为旧值（通常 `false`） | 图像生成模型**出现在对话模型列表**里，被当普通模型选中 → 调用报错或产出乱码 |
| §3.1 分支二（有快照） | 同上，且 `update_if_untouched` 不覆盖该字段 | 同上 |
| §3.2 迁移补丁 | 赋值缺失 + 触发条件缺失，**双重不生效** | 同上 |
| `CapabilityOverrides` | 不涉及（独立旁路） | 无 |

**关键特征：三者都「静默」** —— 不报错、不告警、无日志。因为都是 `bool` 字段的「不赋值」，
Rust 编译器不会提示（字段有 `#[serde(default)]`，结构体字面量在别处已满足）。
这正是 `modeFamily.ts` 那类注释反复警告的「加字段但判据点没跟上」在 Rust 侧的等价形态。

**影响面**：`anki_model_routing.rs:153`、`model_selection.rs:31-33`、`mod.rs:2775` 三处**硬依赖** `!is_image_generation` 做排除。
标记丢失 → 这些排除失效 → 图像生成模型混入制卡路由、上下文压缩选型、OCR 候选。
