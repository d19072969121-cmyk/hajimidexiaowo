# E13-D 输入吞字定位报告

**任务**：task-4 / E13-D —— 定位「主页输入文字没显示 / 被吞」的根因
**仓库**：`/root/workspace/repos/deep-student` 分支 `diy/m1-build-baseline`
**方法**：纯代码 + 单元测试（用户明确不能截屏、模型无法识图）
**结论一句话**：**根因已证实 —— 移动端中文 IME 组合期间 `ComposerTextarea.onChange` 主动跳过 store 回写，受控组件立刻把 DOM 回滚成旧值，用户当场敲的字被抹掉。与重渲染无关。**

---

## 1. 根因（已实证）

### 1.1 缺陷代码

`src/features/chat/components/input-bar/ComposerTextarea.tsx:139` textarea 是**受控**组件：`value={inputValue}`。

修复前 `:168-172`：

```tsx
onChange={(e) => {
  // 🔧 IME 合成期间跳过 store 更新，仅移动端 WKWebView 需要（桌面端受控组件会阻止输入）
  if (!isComposingRef.current || !isMobile) {
    onInputChange(e.target.value);
  }
```

对**移动端**（`isMobile === true`）而言，条件化简为 `!isComposingRef.current`：**组合期间不写 store**。

### 1.2 真正的因果链（关键：抹除发生在 onChange 的返回值处，不是重渲染）

受控 React 组件的硬性约束：`onChange` 处理完成后，若 DOM 的 value 与 `value` prop 不一致，React 在本次 flush **同步**把 DOM 回滚为 prop 值。

1. 用户敲字 → 浏览器更新 DOM value → 派发 `input` 事件；
2. React 调 `onChange`，`e.target.value` 已是新值（实测为 `"zhong"`）；
3. `isComposingRef.current === true` 且 `isMobile === true` → **条件不成立，`onInputChange` 不被调用**；
4. `inputValue`(store) 仍是旧值（通常 `""`）；
5. React 收尾时发现 DOM(`"zhong"`) ≠ prop(`""`) → **立即回滚 DOM 为 `""`**；
6. 用户看到：字没了。

**决定性证据**（探针 AE / 探针 AD，`/tmp/e13_probe11.log`）：

```
AE1 before input                      = ""
AE2 after setter.call, before dispatch= "你好"    <- DOM 先有了
AE3 after dispatch (sync)             = ""        <- dispatch 后同步就被抹掉
AE4 after act flush                   = ""
AD1 DOM immediately after input event = ""        <- 此时尚未发生任何 rerender
```

`AD1` 是在**零次重渲染**的情况下测到的空值 —— 直接证伪「重渲染触发回滚」这一机制。

### 1.3 在真实组件上复现（非探针，直接用 `ComposerTextarea`）

`/tmp/e13_real.log`：

```
BA1 DOM while composing (mobile)  = ""
BA1 store writes received         = []          <- 一次都没写 store
BA2 DOM after compositionend      = ""
BA2 store writes received         = [""]
BA2 => user sees: NOTHING (TEXT EATEN)

BB1 DOM while composing (desktop) = "你好"      <- 桌面正常
BB2 DOM after compositionend      = "你好"
BC1 DOM after plain typing (mobile) = "hello"   <- 非 IME 输入正常
```

**症状完全吻合用户描述**："有时候输入文字，它没有显示 / 被吞了" ——
- 只在**移动端**手机中文输入法（组合态）下发生 → 桌面/英文/直接粘贴都正常，所以显得"偶发"；
- 用户感知的"有时候"取决于是否走 IME 组合，而非随机时序。

## 2. 对 Lead 推断的复核（结论：机制环节判错，结论方向正确）

Lead 的因果链第 4 步是「一旦发生重渲染，React 用旧 `inputValue` 回写 DOM → 组合内容被抹掉」。**这一环不成立**：

| Lead 主张 | 实测 | 判定 |
|---|---|---|
| 组合内容被抹除 | 是 | ✅ 成立 |
| 触发条件是**重渲染** | 不是。`AD1` 显示 **0 次重渲染**即被抹除；回滚发生在 `onChange` 的同步 flush 内 | ❌ 判错 |
| 移动端 guard 是必要条件 | 是 | ✅ 成立 |
| `!isMobile` 跳过是根因 | 是 | ✅ 成立 |

判错的实际影响：按「重渲染触发」的模型去修（例如只优化 `LearningHubPage` 依赖数组、减少重渲染），**修不掉吞字**。重渲染只是让症状更显眼，不是成因。这一点必须纠正，否则修复会落空。

补充：Lead 探针用的 `fireEvent.change` 与我的 `nativeSetter + input` 两种驱动方式**结论一致**（见 `AA/AB`，`/tmp/e13_probe10.log`），方法学无分歧。

### 2.1 为什么原代码要加 `!isMobile`（先搞清意图再改）

`git show 89e6b672`（"improve IME handling across platforms"）显示完整演进：

```diff
-// 🔧 IME 合成期间跳过 store 更新，防止 WKWebView 重复追加文本
-if (!isComposingRef.current) {
+// 🔧 IME 合成期间跳过 store 更新，仅移动端 WKWebView 需要（桌面端受控组件会阻止输入）
+if (!isComposingRef.current || !isMobile) {
```

原始动机是**修 WKWebView 重复追加文本**（合成结束时 store 补写 + DOM 已含文本 → 重复）。该改动同时发现：无条件跳过会让**桌面端完全无法输入**（正是本报告描述的受控回滚机制，桌面先中招），于是用 `|| !isMobile` 让桌面/英文路径逃生。

**结果：移动端被留在坑里。** 这是一个"为了让桌面能用而把移动端牺牲掉"的补丁，不是移动端真的需要跳过。因此**修复时不能只删 `!isMobile`**，必须同时把「重复追加」保护改成不依赖跳过 store 的形式 —— 否则会踩回原作者已经踩过的 WKWebView 重复 bug。

## 3. 最小修复（已实施，附 diff）

**思路**：受控组件的 store 必须无条件跟随 DOM（这是受控模型的硬约束，不是可选项）；把「重复追加」保护从"跳过写入"改为**按值去重**。

```diff
@@ ComposerTextarea.tsx
   // 🔧 IME 合成态追踪：防止 WKWebView 中文输入法重复追加文本
   const isComposingRef = useRef(false);
+  // 🔧 记录最后一次已写入 store 的 DOM 值，供 compositionend 去重
+  // （受控组件下 store 与 DOM 必须始终一致，重复写入会让受控值漂移）
+  const composedTextRef = useRef('');

@@ onCompositionEnd
-            // 合成结束时用最终值同步 store，确保不丢字
-            const composedTarget = e.target as HTMLTextAreaElement;
-            onInputChange(composedTarget.value);
-            onCaretPosChange(composedTarget.selectionStart);
+            // 合成结束：store 已在 onChange 中实时跟随，这里只在值确实变化时补一次同步，
+            // 兼顾 WKWebView 偶发不派发最后一个 input 事件的时序（去重避免重复追加）。
+            const composedTarget = e.target as HTMLTextAreaElement;
+            if (composedTarget.value !== composedTextRef.current) {
+              composedTextRef.current = composedTarget.value;
+              onInputChange(composedTarget.value);
+            }
+            onCaretPosChange(composedTarget.selectionStart);

@@ onChange
-            // 🔧 IME 合成期间跳过 store 更新，仅移动端 WKWebView 需要（桌面端受控组件会阻止输入）
-            if (!isComposingRef.current || !isMobile) {
-              onInputChange(e.target.value);
-            }
+            // 🔧 受控组件必须无条件回写 store：DOM 值一旦与 value prop 不一致，
+            // React 会在本次 onChange 返回时同步把 DOM 回滚到旧 prop —— 组合期间
+            // 跳过写入 = 用户敲的字当场被抹掉（E13-D 实测）。
+            // 原 WKWebView「重复追加」保护改由 composedTextRef 去重承担，见 onCompositionEnd。
+            const nextValue = e.target.value;
+            composedTextRef.current = nextValue;
+            onInputChange(nextValue);
```

`isComposingRef` **保留**（仍被 `isImeComposing` 用于 Enter 发送判定），只是不再门控 store 写入。

**候选方案评估**：
- 候选1（本案采用）—— 组合期间也写 store + 去重：改动 3 处、无受控/非受控切换、同时保住 WKWebView 保护。✅
- 候选2（`defaultValue` 非受控兜底）—— 受控↔非受控切换会让 React 丢弃后续 prop 同步，且 store 仍是唯一真相源，切换后需要额外逆向同步。❌ 引入更大风险。
- 候选3（ref 直连 store）—— 绕开重渲染覆盖属于治标，且与本 bug 的真实机制（同一次 `onChange` 内同步回滚）无关，不能解决问题。❌

## 4. 一并排查：另外两条嫌疑路径

### 4.1 长文本粘贴 `indexOf` 首匹配（真实缺陷，但非本次症状成因）

`InputBarUI.tsx:1009-1012`：

```ts
const index = inputValue.indexOf(text);
const nextValue = inputValue.slice(0, index) + inputValue.slice(index + text.length);
```

用**首次出现位置**定位片段。若该片段文本在输入框中出现两次（或其内容恰好是用户已输入文本的子串），会**剥错区间**：

```
输入 "PASTEDPASTED"，剥离 "PASTED" -> 结果 "PASTED"   (剥掉第一个，留下真正粘贴的那个)
输入 "PREFIX-PASTED-PASTED"      -> "PREFIX--PASTED"  (删中段，非粘贴段)
```

**但这条不构成"输入被吞"的主因**：
- 仅在用户**点击建议条「转为附件」按钮**时执行，**打字过程中不会触发**；
- 触发门槛是粘贴 >1000 字符（`inputBarConfig.ts:31`），门槛较高。

**判定：未证实与本症状相关**。属独立低危缺陷，建议后续用「记录粘贴落点 range」替代 `indexOf`，本轮不改（避免与主修复混在一起）。

### 4.2 受控值来源竞态（已排除）

- `InputBarV2.tsx:449-462` 草稿恢复受 `draftRestoredKeyRef` 一次性门控，且 `restoreComposerDraftIfSafe`（`composerDraftStorage.ts:50`）要求 `inputValue === ''`，打字中不会触发；
- `InputBarUI.tsx:1026-1034` armed effect 只在 `longPasteCandidate` 非空时监控，普通打字不触发（`longPasteCandidate` 为 `null` 时首行 `return`）；
- `:1036-1038` `sessionSwitchKey` 重置只在会话切换时执行。

**判定：未证实存在覆盖打字的异步回写路径**。

### 4.3 inert / aria-hidden 吞事件（已排除）

`ComposerTextarea` 的 textarea 上无 `inert`/`aria-hidden`；输入栏在 `MobileSlidingLayout` 中不进入 inert 分支。本案的抹除发生在 **React 受控回滚**层面，与 inert 无关（若为 inert 吞事件，DOM 根本不会先出现 `"你好"`，而 `AE2` 显示它出现了）。

## 5. 证据强度自评

| 项 | 强度 | 依据 |
|---|---|---|
| 根因＝移动端 IME 组合期间跳过 store 回写导致受控回滚 | **高（已实证）** | 真实组件复现 + 逐时序 DOM 采样（AE1→AE4/AD1），零重渲染即被抹除 |
| 「触发条件是重渲染」这一说法 | **高（已证伪）** | AD1：无重渲染仍被抹除 |
| 修复有效性 | **高** | 5 场景转绿 + 260 用例无回归 |
| 长文本 `indexOf` 缺陷 | **中** | 逻辑推演 + 纯函数验证，未构造端到端复现，且与主症状门槛不符 |
| 竞态 / inert 路径 | **排除** | 代码条件门控分析 |

**残留不确定性**：jsdom 与真机 WebView 的差异。jsdom 通过 `HTMLTextAreaElement.prototype.value` 的 native setter 驱动 React，与真机浏览器原生更新 DOM 后派发 `input` 的路径在受控回滚这一 React 行为上一致（受控回滚是 React 自身逻辑，不依赖宿主环境）；但**IME 事件序列时序**（如 WKWebView 是否在组合期派发 `input`）jsdom 无法完全保真。建议真机验证项见第 6 节。
