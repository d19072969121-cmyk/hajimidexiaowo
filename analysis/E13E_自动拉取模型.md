## 2. 按钮位置与行为

**位置**：模型列表头部工具栏内，`fetch_models_button`（获取模型列表）之后、`add_model_button`（添加模型）**之前** —— 即用户要求的「添加模型上面」。测试用 `compareDocumentPosition` 断言 DOM 顺序锁定这一点。

**显示条件**：与既有按钮同一套闸门 `!isCodexOAuthVendor && onAddVendorModels && supportsModelFetching(providerType)`，Codex OAuth 供应商不渲染（无通用模型列表接口）。

**行为**：`handleAutoFetchModels` 复用既有底座，不新写 HTTP ——
1. 无 `baseUrl` → warning `need_base_url`，不发请求；
2. `resolveApiKey(vendor)`，`authMode==='none'` 早返回 `''`；返回 `null` → warning `need_api_key`；
3. `fetchModelsFromVendor(vendor, key)`（Tauri 走 `fetch_vendor_models`，浏览器态走前端实现）；
4. 按 `selectedVendorModels[].profile.model` 小写集合去重，只提交新模型；
5. `onAddVendorModels` 一次性全量提交（label / contextWindow / maxOutputTokens 原样带过）；
6. 提示：成功带 count；`newModels.length===0` → `auto_fetch_models_empty`（不静默）；异常 → `INVALID_VENDOR_MODEL_RESPONSE` 映射成 `invalid_response` 文案，其余错误原样带出 HTTP 状态与响应体。

`disabled={autoFetchingModels || vendorBusy}`，loading 时按钮文案换成「正在拉取模型…」+ Spinner。

## 3. 免 Key 供应商拉取路径 —— **验证通过**

pollinations / llmtech / kilo（`auth_mode='none'`）**单测已覆盖且通过**，三层证据：

1. **前端**：`resolveApiKey` 首行 `if (vendor.authMode === 'none' || vendor.noApiKey) return '';` → 不读 key、不报 `need_api_key`；`fetchOpenAICompatible` 里 `apiKey ? {Authorization: ...} : {}` → 请求头**不带 Authorization**。
2. **测试断言**（三家用例参数化跑）：`requestInit.headers` 的 key 小写集合不含 `authorization`；URL 为 `{baseUrl}/models`；`onAddVendorModels` 收到 2 个模型。即：**mock fetch 验证了不带 Authorization 也能走通**。
3. **后端（真机路径）**：Tauri 态走 `fetch_vendor_models`（`src-tauri/src/commands.rs:2605`）—— `uses_no_auth` 时跳过密钥校验；`vendor_models_endpoint` 对这三家 provider_type 落入 `_` 分支 → `{base}/models`（`/openai`、`/v1`、`/api/gateway` 后缀均不匹配剔除规则，故保留并追加 `/models`）；`vendor_model_headers` 的 `"openai" if !key.is_empty()` 不命中 → 无 Authorization。**结论：后端天然免 Key 可拉，无需改动。**
   另一个前提也已核实：`vendor_configs_for_runtime → load_builtin_vendor_profiles` 不经过 `read_user_vendor_configs` 的 `continue` 分支，且 `vendor.auth_mode.is_some()` 时会把内置模板的 `auth_mode` 重新注入已持久化的用户副本，因此**旧副本不会因缺 `authMode` 而使免 Key 供应商掉进 `need_api_key`**。

## 4. 失败用例的修法（「拉取进行中禁用按钮」）

原写法在 `fireEvent.click` 之后**同步** `getByRole('button', { name: '..._fetching' })`。而 testing-library 的 `fireEvent` 走 act 包裹的现代事件路径，状态提交是调度的；同步查询时按钮文案仍是旧的 → `getByRole` 抛错 → 后面的 `resolveFetch?.()` 永不执行 → fetch promise 永不 settle → 兜底 `waitFor` 超时，报出误导性的 "spy not called"。

最终修法（实测可复现）：

```ts
await act(async () => {
  autoFetch.click();          // 原生 click()：React 走 legacy discrete 路径，setState 在 dispatch 内同步 flush
  await Promise.resolve();
});
const busy = screen.getByRole('button', { name: '..._fetching' });
expect(busy).toBeDisabled();
await waitFor(() => expect(tauriFetchMock).toHaveBeenCalledTimes(1));  // 把「请求确实发出」钉死
```

> 先试过 Lead 建议的 `findByRole`：**本文件里不成立** —— `findBy`/`waitFor` 的每次重试都在 act 内再 flush 一次，fetch microtask 会在等待期间被推进，随后 `setAutoFetchingModels(false)` 把按钮复原成非 loading 文案，于是 `findByRole(..._fetching)` 仍超时。改用原生 `click()` 才是确定性的解法，跑 3 次均 11/11。`fireEvent` 保留给其余用例（那些是 fail-fast 的负向断言，不受影响）。

## 5. `disabled` 与 finally 复位 —— 无永久禁用缺陷

`handleAutoFetchModels` 的 `try { ... } finally { setAutoFetchingModels(false); }`（`VendorDetailPanel.tsx:472-474`）覆盖所有出口：正常返回、`return` 提前退出（无 baseUrl / 无 key / 无新模型）、以及任何 throw。只有两条 early return 在 `setAutoFetchingModels(true)` **之前**（无 vendor / 无回调），此时状态本来就没被置起。拉取抛异常 → `catch` 提示后必然进 `finally` → 按钮恢复可点。测试用例「拉取进行中禁用按钮并显示 loading 文案，结束后自动复位」正是锁这一条：loading 中 `toBeDisabled()`，settle 后回到可点且不再显示 loading 文案。
